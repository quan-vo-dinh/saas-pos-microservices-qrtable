## Implementation Constraints

- Kitchen state must be Redis-only.
- Do not add any Kitchen TypeORM entity or database migration.
- Do not implement batching, batch DTOs, batch keys, or grouped quantities.
- A single order can create at most one ticket per `(tenantId, orderId, station)`.
- Kafka delivery is at-least-once; ticket creation must be idempotent by
  `eventId` and `(tenantId, orderId, station)`.
- Missing item `station` goes to `kds:{tid}:dead-letter:order-confirmed` and
  must not silently fallback to category.
- BFF queue events must be caused by internal Redis Pub/Sub, not direct Kafka
  `order.confirmed`.
- `MARK_READY` only mutates Kitchen Redis here; Order sync happens in Batch 5
  through BFF after Batch 4 provides Order TCP commands.
