## Current State

### What Already Works

- Catalog table creation stores a `qrToken`.
- Catalog validates QR tokens through TCP.
- BFF exposes `POST /menu/validate-qr`.
- BFF exposes `POST /customer/sessions/join`.
- Customer PWA reads `table` and `token` query params.
- Customer PWA already persists joined session metadata including backend
  `tenantId`.
- Management App table service already supports `POST /admin/tables/:id/regenerate-qr`.

### Gaps

1. **POS QR dialog is not a QR image.** It displays a Lucide placeholder icon and
   a hardcoded URL.
2. **Download is not implemented.** The current button logs to console.
3. **QR token regenerate is not a real revoke.** Current token generation is
   deterministic from `tableId + tenantId`, so regenerating returns the same
   token unless the secret changes.
4. **QR validation ignores the stored token.** Current validation recomputes the
   expected token instead of comparing against `table.qrToken`.
5. **PWA dynamic tenant is not complete.** Customer PWA falls back to
   `VITE_TENANT_ID`; QR URL does not resolve a public tenant slug.
6. **Repeated scan risk.** Current Order session join creates a new session after
   QR validation. A second guest scanning an occupied table should join the
   active table session, not create a new competing session.

## Locked Decisions

- QR URL exposes **tenant slug**, not internal tenant id.
- Dev QR URL uses query params first:

  ```txt
  http://localhost:<customer-pwa-port>/?tenant=<tenantSlug>&table=<tableId>&token=<qrToken>
  ```

- Production can later support subdomain:

  ```txt
  https://<tenantSlug>.qrtable.io?table=<tableId>&token=<qrToken>
  ```

- Batch 6 implements query-param slug resolution now. Subdomain support is a
  documented follow-up, not required.
- PWA resolves `tenantSlug -> tenantId` before calling QR validation or session
  join.
- BFF owns the public tenant resolver endpoint.
- QR image is generated client-side in Management App with `qrcode.react`.
- QR image is a derived artifact and is not stored in PostgreSQL or Cloudinary in
  this batch.
- Catalog stores only `table.qrToken`.
- QR token becomes opaque random token. Regenerate replaces `table.qrToken` and
  invalidates old printed QR codes.
- Order join session returns an existing active session when the table is already
  occupied by a session.

## Architecture

### Tenant Slug Resolver

Add a public BFF endpoint:

```txt
GET /public/tenants/:slug
```

Response data:

```ts
type PublicTenantResolveResponse = {
  id: string;
  slug: string;
  name: string;
  isActive: boolean;
};
```

Behavior:

- BFF calls SaaS TCP `SAAS.GET_BY_SLUG`.
- SaaS service loads tenant by slug.
- If tenant does not exist, return `SAAS_TENANT_NOT_FOUND`.
- If tenant exists but `isActive === false`, return a forbidden/inactive tenant
  error using existing error handling style where possible.
- Endpoint is public and must not require `UserGuard`.
- Endpoint must not return internal subscription/billing fields.

Required shared additions:

- `TCP_REQUEST_MESSAGE.SAAS.GET_BY_SLUG`
- `GetTenantBySlugTcpRequest = { slug: string }`
- Public gateway response DTO, or reuse `TenantResponseDto` if no extra fields
  are exposed.

### Current Tenant Metadata For Management App

Management App currently has `profile.tenantId` through auth, but it should not
guess `tenantSlug` from env or local constants.

Add a protected BFF endpoint for tenant staff screens:

```txt
GET /admin/tenant/current
```

Behavior:

- Requires `@Authorization({ secured: true })`.
- Requires `@Permissions([PERMISSION.CATALOG_GET_LIST])` because the QR dialog is
  part of table/catalog management and this avoids adding a new permission in
  Batch 6.
- Reads current request tenant id from `TenantGuard`.
- Resolves the current tenant against SaaS without assuming the request tenant
  value is always a SaaS UUID:
  - if the value is UUID-shaped, call `SAAS.GET_BY_ID`;
  - otherwise call `SAAS.GET_BY_SLUG` using a legacy/public tenant key when
    compatibility requires it.
- Returns the same public tenant metadata shape:

```ts
type CurrentTenantPublicResponse = {
  id: string;
  slug: string;
  name: string;
  isActive: boolean;
};
```

Management App QR dialog uses this endpoint to obtain `tenantSlug`.

Seed dev sạch hiện dùng id tenant nội bộ `023772bb-391b-401c-936a-ed7034b69cec`
và slug công khai `pho-viet`. Backend có thể giữ phủ resolver legacy `tenant_a`
chỉ để tương thích, không coi là đường seed chuẩn.

### QR Token Semantics

Current deterministic HMAC token is replaced with an opaque random token:

```ts
randomBytes(32).toString('hex');
```

Create table:

```txt
create table row with temporary token
→ generate random token
→ update table.qrToken
```

Regenerate QR:

```txt
load table by tenantId + tableId
→ generate new random token
→ update table.qrToken
→ return updated table
```

Validate QR:

```txt
load table by tenantId + tableId
→ compare provided token with table.qrToken using timingSafeEqual
→ return table if equal
→ reject if token mismatch
```

Security notes:

- Compare buffers only after checking equal byte length.
- Keep token length stable at 64 hex chars.
- Existing unique index `(tenantId, qrToken)` remains useful.
- Old QR codes stop working after regenerate.

### POS QR Rendering

Management App table QR dialog builds the customer URL from:

- `NEXT_PUBLIC_CUSTOMER_PWA_URL`
- current tenant slug from `GET /admin/tenant/current`
- `currentTable.id`
- `currentTable.qrToken`

Canonical builder:

```ts
buildCustomerQrUrl({
  baseUrl,
  tenantSlug,
  tableId,
  qrToken,
});
```

Output:

```txt
<baseUrl>/?tenant=<tenantSlug>&table=<tableId>&token=<qrToken>
```

UI behavior:

- Render a real QR with `QRCodeSVG`.
- Keep the URL visible in monospace.
- Copy URL copies the exact QR URL.
- Open PWA opens the exact QR URL in a new tab.
- Download PNG downloads the exact QR image.
- Print uses the existing print behavior or a focused printable QR area.
- Regenerate QR calls existing `tablesService.regenerateQr(id)`, invalidates
  table queries, and updates the QR image when the table query returns the new
  token.

Library decision:

- Use `qrcode.react` in `management-app`.
- Use `QRCodeSVG` for display/print.
- Use `QRCodeCanvas` or a canvas rendered in the dialog for PNG download.
- Do not use a backend QR image endpoint in this batch.

### Customer PWA Dynamic Tenant Flow

PWA landing now reads:

- `tenant` public slug
- `table`
- `token`

Flow:

```txt
parse URL
→ if tenant/table/token missing: show scan-required state
→ GET /public/tenants/:slug
→ set transient tenant id in customerApi
→ POST /menu/validate-qr with x-tenant-id
→ user clicks "Vào Menu"
→ POST /customer/sessions/join with x-tenant-id
→ persist session returned by backend
→ later customer APIs use persisted session.tenantId and x-session-id
```

Rules:

- `tenantSlug` is only public routing input.
- `tenantId` comes from resolver response and backend session response.
- `VITE_TENANT_ID` remains only as a dev fallback for legacy URLs without
  `tenant`.
- If URL contains `tenant`, resolver result overrides `VITE_TENANT_ID`.
- If resolver fails, do not call QR validation.
- If QR validation fails, do not call join session.

### Order Session Join Semantics

Current join session behavior must become idempotent at table-session level.

After QR validation returns a table:

```txt
if table.status === AVAILABLE:
  create new ACTIVE session
  update Catalog table status to OCCUPIED with sessionId
  return new session

if table.status === OCCUPIED and table.sessionId exists:
  load active Order session by tenantId + table.sessionId
  if active session exists:
    refresh session activity/cache as existing service convention allows
    return existing session
  if session missing:
    return a clear session/table inconsistency error

if table.status === BILLING:
  reject with clear message: table is billing and cannot accept new ordering

if table.status === CLEANING:
  reject with clear message: table is being cleaned
```

Expected demo result:

- First phone scan creates the session.
- Second phone scan of the same QR joins the same active session.
- Regenerated QR invalidates old QR URL for future scans.
- Existing active sessions do not need to be killed by QR regeneration.

## Data Ownership

| Data                         | Owner           | Storage                    | Notes                                              |
| ---------------------------- | --------------- | -------------------------- | -------------------------------------------------- |
| Tenant `id`, `slug`, `name`  | SaaS Service    | `tenants` PostgreSQL table | Slug is public route key; id remains internal key. |
| Table `qrToken`              | Catalog Service | `tables.qr_token`          | Opaque random token.                               |
| QR image                     | Management App  | Derived in browser         | No DB/Cloudinary storage in Batch 6.               |
| Customer active tenant id    | Customer PWA    | In-memory, then session LS | Resolver result before join, session after join.   |

## Error Handling

PWA landing states:

- Missing `tenant`, `table`, or `token`: show scan-required state.
- Tenant resolver pending: show resolving tenant state.
- Tenant not found/inactive: show invalid restaurant QR state.
- QR validation pending: show current validation loading state.
- QR invalid: show current invalid QR state.
- Join session fails because table is billing/cleaning: show staff-help message.

POS QR dialog states:

- Current tenant query pending: show loading state in the dialog.
- Current tenant query failed or missing slug: disable QR display and show
  configuration error.
- Missing `qrToken`: show table QR unavailable state and offer regenerate if
  table id exists.
- Regenerate pending: disable regenerate/download/open buttons.
- Regenerate success: toast and update QR URL after query invalidation.
- Download failure: toast error and keep URL copy available.

Backend errors:

- Tenant slug not found: existing `SAAS_TENANT_NOT_FOUND`.
- Tenant inactive: use a clear forbidden business error. If no existing error
  code fits, add a focused `SAAS_TENANT_INACTIVE`.
- QR mismatch: existing `CATALOG_TABLE_INVALID_QR_TOKEN`.
- Occupied table with missing Order session: add or reuse a clear session/table
  inconsistency error.
- Billing/cleaning table join: return a clear business exception. Reuse existing
  table/session error codes only if the UI can display them accurately.

## Security And Multi-Tenant Rules

- QR URL contains public tenant slug, not internal tenant id.
- PWA must resolve slug through BFF/SaaS before sending tenant-scoped requests.
- Public tenant resolver only returns public fields: `id`, `slug`, `name`,
  `isActive`.
- `x-tenant-id` is still the BFF tenant context mechanism after resolver.
- QR token is table-scoped and tenant-scoped by validation query.
- Regenerating QR invalidates only future scans with old URLs. It does not close
  an already active session.
- Never accept `tableId + token` without tenant context.
