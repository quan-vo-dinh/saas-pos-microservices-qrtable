# Step 1.6 — Frontend ↔ Backend Integration Design

> **Phase:** 1 — Catalog + Menu + Table
> **Status:** Approved
> **Date:** 2026-04-15

## Problem Statement

Step 1.5 delivered a fully functional Catalog Service (TCP) and BFF proxy layer (REST). Frontend apps (Management App + Customer PWA) were built with mock data during Steps 1.2/1.3. The API paths and base URLs in frontend code are placeholders that don't match the actual BFF routes. Step 1.6 bridges this gap — replacing mock data with real API calls and adding mutation capabilities.

## Root Cause of Current Mismatches

Frontend services were created on 2026-03-26 (Step 1.2/1.3) with speculative API paths before the backend routes existed. Backend routes were finalized on 2026-04-12 (Step 1.5). This is expected in mock-first development — Step 1.6 is the designated alignment step.

### Specific Mismatches

| Frontend Expects            | BFF Actual               | Resolution                       |
| --------------------------- | ------------------------ | -------------------------------- |
| Base URL `localhost:3300`   | BFF on port `3000`       | Use env variable, default `3000` |
| `/catalog/categories`       | `/admin/categories`      | Fix frontend paths               |
| `/catalog/menu-items`       | `/admin/menu-items`      | Fix frontend paths               |
| `/catalog/areas`            | `/admin/areas`           | Fix frontend paths               |
| `/catalog/tables`           | `/admin/tables`          | Fix frontend paths               |
| `/customer/menu/categories` | `GET /menu` (full menu)  | Refactor to single endpoint      |
| `/customer/menu/items`      | `GET /menu` (full menu)  | Refactor to single endpoint      |
| `/customer/session/verify`  | `POST /menu/validate-qr` | Fix endpoint path                |

## Architecture Decisions

| Decision                   | Choice                                                                                        | Rationale                                                            |
| -------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Customer PWA menu fetching | Single `GET /menu` call, parse client-side                                                    | Leverages BFF cache (10 min), reduces N+1 to 1 request, mobile-first |
| Base URL configuration     | Env variables (`VITE_BFF_URL`, `NEXT_PUBLIC_BFF_URL`), default `http://localhost:3000/api/v1` | Flexible for deployment                                              |
| Optimistic updates         | Not in Phase 1 — invalidate + refetch                                                         | Simpler, sufficient for admin CRUD UX                                |
| Image upload progress      | XMLHttpRequest wrapper with `onProgress`                                                      | Native browser, no extra dependency                                  |
| Error feedback             | Toast notifications (shadcn Sonner)                                                           | Consistent, non-blocking UX                                          |
| WebSocket real-time        | Not in Phase 1 (Phase 2B)                                                                     | Users refresh to see updates                                         |

## Approach: Layer-by-Layer (Bottom-Up)

Each layer is verified before building the next. This ensures a stable foundation.

```
Layer 1: Config (env vars, base URLs, paths)
    ↓
Layer 2: Services (API call functions)
    ↓
Layer 3: Hooks (TanStack Query queries + mutations)
    ↓
Layer 4: UI (replace mock → hooks, add states)
    ↓
Layer 5: E2E Verification
```

### 2E. Upload Client Utility (new — shared lib)

**File:** `libs/frontend/utils/src/lib/upload-client.ts`

```typescript
export type UploadOptions = {
  fieldName?: string; // form field name, default 'file'
  onProgress?: (percent: number) => void;
  headers?: Record<string, string>;
};

export function uploadFile<T>(url: string, file: File, options?: UploadOptions): Promise<T> {
  return new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest();
    const formData = new FormData();
    formData.append(options?.fieldName ?? 'file', file);

    xhr.upload.addEventListener('progress', (e) => {
      if (e.lengthComputable && options?.onProgress) {
        options.onProgress(Math.round((e.loaded / e.total) * 100));
      }
    });

    xhr.addEventListener('load', () => {
      if (xhr.status >= 200 && xhr.status < 300) {
        const response = JSON.parse(xhr.responseText);
        // Unwrap BFF response wrapper if present
        resolve(response.data ?? response);
      } else {
        reject(new Error(`Upload failed: ${xhr.status} ${xhr.responseText}`));
      }
    });

    xhr.addEventListener('error', () => reject(new Error('Upload failed: network error')));
    xhr.open('POST', url);

    if (options?.headers) {
      Object.entries(options.headers).forEach(([key, value]) => {
        xhr.setRequestHeader(key, value);
      });
    }

    xhr.send(formData);
  });
}
```

Export from `libs/frontend/utils/src/index.ts`.

### Auth Header Integration (Step 1.25 — RESOLVED)

Step 1.25 (NextAuth + Keycloak) is **already complete**. `auth.ts` stores `accessToken` in session.

**Solution: Authenticated API Client (Decorator Pattern)**

Create `authApiClient` in Management App that wraps the generic `apiClient` and automatically injects auth headers:

```typescript
// apps/management-app/src/lib/api/authenticated-client.ts
import { apiClient, type ApiClientOptions } from '@einvoice/frontend-utils';
import { auth } from '@/auth';
import { getBffBaseUrl } from '@/lib/auth/bff-server';

export async function authApiClient<T>(path: string, options?: ApiClientOptions): Promise<T> {
  const session = await auth();
  return apiClient<T>(path, {
    ...options,
    baseUrl: options?.baseUrl ?? getBffBaseUrl(),
    headers: {
      ...options?.headers,
      ...(session?.accessToken ? { Authorization: `Bearer ${session.accessToken}` } : {}),
      ...(session?.user?.tenantId ? { 'x-tenant-id': session.user.tenantId } : {}),
    },
  });
}
```

For client-side (`'use client'`), create a hook-based version using `useSession()`.

Service files replace `apiClient` → `authApiClient`. This follows:
- **Single Responsibility**: shared `apiClient` stays auth-agnostic
- **Open/Closed**: `apiClient` not modified, extended via composition
- **DRY**: Auth logic centralized in one wrapper
