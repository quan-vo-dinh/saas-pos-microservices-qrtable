# Step 2.5 FE-BE Integration Design

> Date: 2026-04-30  
> Scope: Phase 2A Step 2.5 — Customer PWA and Management POS integration with
> real BFF/Order APIs  
> Status: Draft for owner review  
> Depends on: Step 2.4 implemented Order Service, Redis cart/session, Kafka
> outbox, BFF Direct REST/WebSocket

## Goal

Replace Step 2.2 mock ordering flows with real BFF APIs for Customer PWA and
Management POS while preserving the UX already built in the mock UI.

Step 2.5 completes the internal demo loop:

```txt
Customer PWA joins table session
→ adds items to Redis cart
→ submits order
→ Staff POS sees pending order by polling
→ staff confirms/cancels through BFF
→ customer tracking updates from refetch and minimal WebSocket hints
```

## Current Backend Contract

### Customer REST

All routes go through BFF under `http://localhost:3300/api/v1`.

Session:

- `POST /customer/sessions/join`
  - body: `{ tableId, qrToken }`
  - returns: `Session`

Cart/order:

- `GET /customer/cart`
- `PATCH /customer/cart`
  - body: `{ expectedCartVersion, operation, menuItemId?, cartLineId?, quantity?, note?, sessionClientId? }`
- `DELETE /customer/cart?expectedCartVersion=N`
- `POST /customer/orders`
  - body: `{ expectedCartVersion, idempotencyKey, notes? }`
- `GET /customer/orders/:id`
- `DELETE /customer/orders/:id`
  - body: `{ reason? }`

Service/bill:

- `POST /customer/service-requests`
  - body: `{ type, note? }`
- `POST /customer/bill/request`
- `GET /customer/bill/current`

Customer order/cart routes require:

- `x-tenant-id`
- `x-session-id` after successful `POST /customer/sessions/join`

The BFF `SessionGuard` uses `x-session-id` for customer order routes. Customer
PWA must persist the Order session ID returned by join and send it on every
customer order/cart/bill/service request call.

### Staff REST

Orders:

- `GET /admin/orders?status=&tableId=&limit=&offset=`
- `GET /admin/orders/:id`
- `POST /admin/orders/:id/confirm`
- `POST /admin/orders/:id/cancel-pending`
- `POST /admin/orders/:id/cancel-processing`

Service requests:

- `POST /admin/service-requests/:id/acknowledge`
- `POST /admin/service-requests/:id/resolve`

Bill/table:

- `POST /admin/bills/:sessionId/reopen`
- `POST /admin/tables/transfer`

Staff routes require:

- `Authorization: Bearer <token>`
- `x-tenant-id`
- BFF permissions from `docs/architecture/permission-matrix.md`

### WebSocket

Namespace:

```txt
/orders
```

Client joins:

- `join.session` with `{ sessionId }`
- `join.staff` with `{ tenantId }`

Server emits:

- `events.cartUpdated`
- `events.orderCreated`
- `events.orderStatusChanged`
- `events.serviceRequested`
- `events.billRequested`
- `events.tableTransferred`

WebSocket events are hints only. Clients must refetch canonical REST data after
receiving a relevant event or reconnecting.

## Scope Decisions

### In Scope

Customer PWA:

- Replace mock menu/cart/order/service request behavior with real API calls.
- Use real Order session from `POST /customer/sessions/join`.
- Persist session metadata and send `x-session-id` on customer APIs.
- Use React Query for server state.
- Use optimistic cart updates with rollback/refetch on `CART_VERSION_CONFLICT`.
- Submit order with idempotency key and keep success animation/redirect.
- Tracking page reads real order detail and responds to WS status hints.
- Service request buttons call real API.
- Bill request calls real API and locks ordering when bill/cart status indicates
  billing.

Management POS:

- Replace live order list mock with `GET /admin/orders` polling.
- Replace confirm/cancel actions with real BFF calls.
- Keep POS visual density, filters, inspector, and cancel dialog UX.
- Use React Query polling for order list/detail.
- Refetch orders after BFF Direct WebSocket hints if staff socket is connected.
- Keep table map backed by existing real Catalog table APIs where already
  available.
- Integrate table transfer with `POST /admin/tables/transfer` only where the UI
  has the required `sessionId`, `fromTableId`, and `toTableId`.

Shared frontend infrastructure:

- Add typed order API service modules for Customer PWA and Management App.
- Add query keys/mutations for cart, order, session, service request, bill, and
  POS order list/actions.
- Normalize response unwrapping for BFF `ResponseDto`.

### Out Of Scope

- BFF Kafka consumer bridge.
- Socket.IO Redis Adapter.
- Full KDS real backend integration.
- Kitchen Service or KDS queue.
- Cash payment confirmation, refunds, split bill, payment gateway.
- Physical Database-per-Service split.
- Fine-grained FE control-level permission mapping beyond existing route/sidebar
  RBAC.
- Offline order queue. Step 2.5 may keep graceful error states, but should not
  add offline write sync.
- Automatic mock fallback when backend services are down. Step 2.2 mock files may
  remain in the repository for reference/dev demos, but primary Step 2.5 order
  paths must use real APIs.

This section records the explicit audit between Step 2.2 mock UI and Step 2.4
backend contracts. These gaps drive the Step 2.5 plan.

| ------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |

| Cart state                | Zustand mock cart owns line state and local version.        | Redis cart snapshot owns `cartLineId`, `cartVersion`, `status`, items.                                         | Use React Query server snapshot as source of truth; optimistic mutations rollback/refetch on conflict.      |

## Proposed Architecture

### Customer PWA Data Flow

Session join:

```txt
QR params / landing form
→ POST /customer/sessions/join
→ persist { sessionId, tableId, tableName, tenantId }
→ set x-session-id for customerApi
→ join Socket.IO room session:{sessionId}:customer
```

Cart:

```txt
GET /customer/cart
→ render cart drawer/pill from CartSnapshot

PATCH /customer/cart
→ optimistic UI update
→ on success replace cart snapshot
→ on CART_VERSION_CONFLICT refetch /customer/cart and show conflict toast
```

Submit:

```txt
POST /customer/orders { expectedCartVersion, idempotencyKey, notes? }
→ keep existing loading/success animation
→ persist lastOrderId
→ navigate to tracking
→ refetch cart and order detail
```

Tracking:

```txt
GET /customer/orders/:id
→ render timeline
WS events.orderStatusChanged
→ invalidate order detail query
```

Service/bill:

```txt
POST /customer/service-requests
POST /customer/bill/request
GET /customer/bill/current
```

Bill/cart locked state should be derived from real cart/bill response instead of
`billLockActive` mock state.

### Management POS Data Flow

Order list:

```txt
GET /admin/orders?status=&tableId=&limit=&offset=
→ React Query polling
→ LiveOrdersTable rows
```

Recommended polling interval:

- 3 seconds for `PENDING` / all live orders in POS.
- 5 seconds for lower-priority filtered views.

Order actions:

```txt
POST /admin/orders/:id/confirm
POST /admin/orders/:id/cancel-pending
POST /admin/orders/:id/cancel-processing
→ invalidate order list and order detail
```

WebSocket:

```txt
connect /orders
emit join.staff { tenantId }
on events.orderCreated / events.orderStatusChanged / events.cartUpdated / events.tableTransferred
→ invalidate relevant queries
```

POS should still work with polling if WebSocket is unavailable.

### Service Request Inbox Decision

Decision: Step 2.5 includes a small backend read contract for staff service
request list so the demo supports the full loop:

```txt
Customer PWA creates service request
→ Staff POS inbox sees request
→ staff acknowledges/resolves through existing endpoints
```

Required backend addition:

- `GET /admin/service-requests?status=&limit=&offset=`
- TCP pattern: `ORDER.SERVICE_REQUEST_GET_LIST`
- tenant-scoped Order Service method returning `ServiceRequest[]`

This remains a narrow read endpoint. It must not expand into notification
history, assignment workflows, SLA reporting, or kitchen/KDS work.

## Error Handling

Customer PWA:

- `CART_VERSION_CONFLICT`: refetch cart, show conflict toast, keep drawer open.
- `BILL_ORDERING_LOCKED`: refetch bill/cart, disable add/submit.
- `ORDER_CART_EMPTY`: refetch cart, show empty-cart state.
- `ORDER_ITEM_UNAVAILABLE` / `ORDER_PRICE_CHANGED`: refetch menu + cart and show
  item-specific toast when possible.
- Network error: keep existing UI state, show retry action.

Management POS:

- `CATALOG_STOCK_INSUFFICIENT`: keep order in pending list, show stock toast.
- Permission errors: show forbidden toast and leave row unchanged.
- Action race/state conflict: refetch order list/detail.
- Polling error: keep last data and show compact degraded-state banner.

## Testing Strategy

Customer PWA:

- Unit-test API services for correct paths, method, body, headers.
- Test session persistence and `x-session-id` injection.
- Test that customer API calls use `localStorage` session metadata to send
  `x-session-id` and do not require a session cookie.
- Test cart conflict handling: mutation error triggers refetch and toast path.
- Typecheck/build PWA.

Management App:

- Unit-test order service paths and authenticated headers.
- Test POS confirm/cancel mutation invalidates order queries.
- Test live orders table can render API data without mock store.
- Test service request list path and acknowledge/resolve invalidation.
- Typecheck/build management app.

Backend integration verification:

- Run Step 2.4 backend services with BFF, Order, Catalog.
- Manual flow:
  1. Join session.
  2. Add cart item.
  3. Submit order.
  4. Confirm in POS.
  5. Verify stock decreases.
  6. Verify PWA tracking refetches to updated status.

## Locked Decisions For Implementation Plan

- Keep KDS real integration out of Step 2.5.
- Keep payment/cash flows out of Step 2.5.
- Use `localStorage` for Customer PWA session persistence and send headers:
  `x-tenant-id` + `x-session-id`. Do not add a cookie requirement in Step 2.5.
- Keep Step 2.2 mock files available for dev/demo, but stop using them on the
  primary PWA/POS order paths. Do not add automatic mock fallback when backend
  services are down.
- Add staff service request list support in Step 2.5:
  `GET /admin/service-requests?status=&limit=&offset=` plus the matching Order
  TCP read contract.

## Acceptance Criteria

- Customer PWA uses real menu/session/cart/order/service-request/bill APIs for
  primary ordering flow.
- Cart mutations use `expectedCartVersion` and handle conflict by refetching.
- Order submit uses idempotency key and preserves success animation/redirect.
- POS live orders use real `GET /admin/orders` polling.
- POS confirm/cancel uses real BFF endpoints and updates list/detail.
- POS service request inbox uses real list/acknowledge/resolve APIs.
- WebSocket hints invalidate/refetch data but are not treated as source of truth.
- No cross-tenant data is exposed.
- KDS, payment confirmation, Kafka bridge, Redis Socket.IO adapter, and
  physical DB split remain out of scope.
