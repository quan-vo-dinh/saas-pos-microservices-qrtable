## Decision 2: Step 2.4 Includes Required Catalog Prerequisites

Step 2.4 must include the Catalog changes required by the business spec:

- Add `MenuItem.station` as the canonical KDS routing source.
- Include station in internal Catalog responses used by Order Service.
- Implement Catalog TCP commands for order flows:
  - `MENU_ITEM.VALIDATE_ORDERABLE`
  - `MENU_ITEM.STOCK_DEDUCT_FOR_ORDER`
  - `MENU_ITEM.STOCK_RELEASE_FOR_ORDER`
- Keep stock mutation inside Catalog Service transactions. Order Service must
  not update Catalog-owned `menu_items` rows directly.

Reason: Order confirmation cannot be correct without Catalog-owned stock locks,
and `order.confirmed` cannot be self-contained for Kitchen/KDS without station
snapshots.

## Decision 3: Database Boundary for Step 2.4

Step 2.4 will implement a **logical Database-per-Service boundary**, not a full
physical database split.

In this step:

- Create a separate `order` Nx app/service.
- Keep Order entities, repositories, services, and TCP handlers owned by the
  Order Service.
- Every Order-domain table includes `tenant_id`.
- Do not add foreign keys from Order tables to Catalog tables.
- Do not query Catalog tables from Order Service.
- Use Catalog TCP for menu validation, stock deduction/release, QR/table
  validation, and table status changes.
- Allow the local dev deployment to keep using the current shared PostgreSQL
  database convention temporarily.

The future target remains:

- Catalog database: `qrtable_catalog`
- Order database: `qrtable_order`
- Payment database: `qrtable_payment`
- SaaS database: `qrtable_saas`

The implementation plan should make the Order config ready for a future split,
for example by supporting `ORDER_TYPEORM_DATABASE` with a fallback to the
current `TYPEORM_DATABASE` / `qrtable` convention.

### Deferred Plan: Physical Database-per-Service Split

The physical split is intentionally out of Step 2.4 because it needs its own
focused plan:

- Docker/PostgreSQL database initialization for multiple service databases.
- Per-service TypeORM configuration.
- Data migration or seed strategy for existing Catalog/SaaS data.
- Migration strategy replacing `synchronize: true`.
- Dev scripts and verification commands for multi-database startup.

Doing this inside Step 2.4 would mix infrastructure migration with Order domain
implementation and increase the risk of losing focus on the core business flow.

## Decision 4: TypeORM Migration Strategy

Step 2.4 will keep the current repo convention temporarily:

- TypeORM `synchronize: true` remains acceptable for this step.
- The implementation plan should note migration hardening as tech debt.
- New entities must still be written as if migrations will be introduced later:
  explicit table names, column names, indexes, tenant columns, and constraints.

Follow-up work should replace `synchronize: true` with explicit TypeORM
migrations after Step 2.4 stabilizes.

## Decision 5: Order Service Ports

Use the ports freed by the Invoice removal note:

```env
ORDER_PORT=3301
ORDER_SERVICE_HOST=localhost
TCP_ORDER_SERVICE_PORT=3201
```

Rationale:

- Existing docs indicate `3301` / `3201` are available after Invoice removal.
- They fit the current service-port style.
- They avoid conflicting with BFF `3300`, Catalog `3005` / `3205`, SaaS
  `3006` / `3206`, and User-Access `3003` / `3203`.

The implementation plan should update `.env.example`, `.env`, TCP config, and
Nx scripts/docs consistently.

## Decision 6: Shared Types Must Be Aligned Before Wiring

Step 2.4 may update shared types to match the canonical spec:

- Add cart line identity fields for Redis cart semantics:
  - `cartLineId`
  - `lineVersion`
  - global `cartVersion` on cart snapshots/events
- Ensure `CartUpdatedEvent` uses cart line shape, not `OrderItem[]`.
- Ensure `OrderConfirmedEvent` includes canonical metadata:
  - `eventId`
  - `eventType: "order.confirmed"`
  - `schemaVersion: 1`
  - `tenantId`
  - `orderId`
  - `sessionId`
  - `tableId`
  - `tableName`
  - station on every item
  - `occurredAt`
  - `correlationId`

Reason: Step 2.4 is the backend contract implementation step. Allowing drift
between shared types and business spec would push contract bugs into Step 2.5
frontend integration.

## Decision 7: Required Packages

The implementation plan should include dependency installation or verification
for the backend runtime:

```bash
pnpm add kafkajs @nestjs/websockets @nestjs/platform-socket.io socket.io
```

Additional Redis command access may be needed for cart/version/lock semantics:

```bash
pnpm add ioredis
```

Rationale:

- Nest Kafka transport requires Kafka client support (`kafkajs`).
- Minimal BFF WebSocket gateway requires Nest WebSocket and Socket.IO server
  packages.
- Current cache-manager usage is suitable for simple get/set cache, but Step
  2.4 needs Redis hash operations, `SET NX` locks, TTL refresh, and atomic cart
  version checks. A direct Redis client is more appropriate for Order Service
  cart/session/transfer-lock logic.
- The direct client must be added as a separate provider library
  `libs/providers/redis-client`, reusing values from
  `libs/configuration/src/lib/redis.config.ts`. It must not replace or duplicate
  the existing `RedisProvider` cache-manager configuration.

Phase 2B can add Socket.IO Redis Adapter separately if/when horizontal WS
scaling is implemented.

## Decision 8: BFF Kafka Bridge Scope

Do **not** implement the BFF Kafka consumer bridge in Step 2.4.

Step 2.4 should implement:

- Order Service publishes Kafka `order.confirmed` via simplified outbox.
- BFF emits direct WebSocket events after successful TCP responses:
  - `order.created`
  - `order.status_changed`
  - `cart.updated`
  - `service.requested`
  - `bill.requested`
  - `table.transferred`

Step 2.4 should not implement:

- BFF consuming `order.confirmed` from Kafka.
- KDS-specific Kafka-to-WebSocket room routing.
- Redis Adapter for multi-instance WebSocket scaling.
- Kitchen Service consumer logic.

Rationale:

- `order.confirmed` is Kafka because Kitchen/Notification/Analytics are
  independent bounded contexts.
- `order.status_changed` is a UI side effect where BFF already has the TCP
  response from Order Service.
- Consuming `order.confirmed` in BFF during Step 2.4 risks duplicate customer/POS
  status events and violates the AP1 rule against using Kafka as a UI proxy.
- Phase 2B is the correct place to harden Kafka bridge + KDS rooms.

## Decision 9: Guard Chain Interpretation

The current BFF global guard chain is:

```txt
UserGuard -> SessionGuard -> TenantGuard -> PermissionGuard
```

For Step 2.4 planning:

- Staff endpoints must use `@Authorization({ secured: true })` and
  `@Permissions(...)`, causing `UserGuard -> TenantGuard -> PermissionGuard`
  to be the effective protected chain while `SessionGuard` bypasses secured
  routes.
- Customer endpoints must omit `@Authorization({ secured: true })`, use
  `SessionGuard -> TenantGuard`, and enforce session ownership in Order Service.
- The plan should avoid a broad global-guard refactor unless a concrete test
  proves the current effective chain is wrong.

Reason: This keeps Step 2.4 aligned with the existing BFF convention and avoids
turning order implementation into a platform-auth refactor.

## Decision 10: Outbox Reliability Scope

Step 2.4 should use the simplified outbox chosen in the architecture docs:

- Write `outbox_events` row in the same Order DB transaction as
  `PENDING -> PROCESSING`.
- Background publisher polls unpublished rows.
- Publish to Kafka topic `order.confirmed` with partition key `tenantId`.
- Mark rows as published after successful Kafka publish.

Full CDC/Debezium or hard transactional outbox infrastructure remains Phase 4A
or a dedicated hardening plan.

## Decision 11: Backend Module Structure Convention

Use the shared `catalog` / `user-access` family pattern for new backend code:

```txt
apps/<service>/src/app/modules/<bounded-context-or-resource>/
  controllers/
  services/
  repositories/
  tests/
  <module>.module.ts
```

The two services are not perfectly identical today:

- Catalog keeps tests in `tests/`.
- User-Access currently keeps `user.service.spec.ts` in `services/`.
- User-Access has `mapper/` and both TCP/gRPC controllers.
- Catalog is TypeORM/PostgreSQL; User-Access is Mongoose/MongoDB.

For Step 2.4, normalize toward the clearer Catalog test-folder convention while
keeping the common module/service/repository/controller structure.

Order Service should use one `OrderModule` bounded context instead of copying
Catalog's one-module-per-resource split. Catalog resources are mostly
independent CRUD/resource modules; Order flows are tightly coupled by session,
cart versioning, bill state, stock locking, table transfer, and outbox
publishing. Splitting these into many Nest modules at this step would increase
import/export churn, transaction coordination, and circular dependency risk
without improving the core delivery.

Entity class names should follow the current shared entity convention:

- Use `Order`, `OrderItem`, `Session`, `Bill`, `ServiceRequest`,
  `OutboxEvent`.
- Do not introduce `OrderEntity` / `SessionEntity` class suffixes unless the
  existing entity convention is changed globally in a separate refactor.

Do not use `apps/saas` as the structure reference for this step because it mixes
legacy top-level folders with module folders.

## Planning Consequence

The Step 2.4 implementation plan should focus on executable backend delivery:

1. Catalog prerequisite contracts.
2. Shared type alignment.
3. Order Service app, entities, repositories, and TCP handlers.
4. Redis cart/session/locks.
5. Order state machine, bill, service request, transfer, cancellation flows.
6. Simplified outbox + Kafka producer.
7. BFF REST endpoints and minimal direct WebSocket gateway.
8. Focused tests around tenant isolation, cart conflicts, stock concurrency,
   idempotency, and event payloads.

The plan should explicitly avoid physical DB splitting and BFF Kafka bridge work
inside Step 2.4.
