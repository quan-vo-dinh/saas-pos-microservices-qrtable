## Lỗi #1: 401 Unauthorized — Missing Authorization Header

### Triệu chứng

- Tất cả API calls đến `/api/v1/admin/*` đều trả về `401 Unauthorized`
- Response body: `{ "message": "invalid_token", "error": "Unauthorized", "statusCode": 401 }`
- User đã login thành công, NextAuth session tồn tại

### Phân tích

Kiểm tra Network tab thấy request headers **không có** `Authorization: Bearer <token>`. `apiClient` (fetch wrapper) không tự động gắn token — nó chỉ là HTTP client thuần, không biết về auth state.

### Nguyên nhân gốc

`authApiClient` (authenticated wrapper) **chưa inject `Authorization` header** vào requests. Code cũ chỉ gửi `x-tenant-id` mà thiếu Bearer token.

### Cách khắc phục

**File:** `apps/management-app/src/lib/api/authenticated-client.ts`

```typescript
// TRƯỚC (thiếu Authorization header)
const authHeaders = {
  'x-tenant-id': tenantId,
};

// SAU (thêm Bearer token)
const authHeaders: Record<string, string> = {};
const accessToken = useAuthStore.getState().accessToken;
if (accessToken) {
  authHeaders['Authorization'] = `Bearer ${accessToken}`;
}
if (tenantId) {
  authHeaders['x-tenant-id'] = tenantId;
}
```

**File:** `apps/management-app/src/lib/auth/auth-store.ts`

```typescript
// Thêm accessToken field vào Zustand store
interface AuthStore {
  profile: UserProfile;
  accessToken: string | null; // ← THÊM MỚI
  setProfile: (profile: UserProfile) => void;
  setAccessToken: (token: string) => void; // ← THÊM MỚI
  clearAuth: () => void;
}
```

**File:** `apps/management-app/src/components/auth/auth-session-hydrator.tsx`

```typescript
// Hydrate accessToken từ NextAuth session vào Zustand
useEffect(() => {
  if (session?.accessToken) {
    setAccessToken(session.accessToken as string);
  }
}, [session?.accessToken]);
```

### Commit

`bf39ec9` — `fix(management-app): add Authorization Bearer token to all API requests`

### Bài học

- API client wrapper phải được thiết kế với auth injection từ đầu
- NextAuth JWT strategy lưu token ở server-side — cần expose qua session callback và hydrate vào client state
- Zustand store là điểm trung tâm cho auth state ở client — mọi API client đều đọc từ đây

## Lỗi #2: 403 Forbidden — Tenant is Required

### Triệu chứng

- Sau khi fix lỗi #1, tất cả `/api/v1/admin/*` endpoints trả về `403 Forbidden`
- Response body: `{ "message": "Tenant is required", "error": "Forbidden", "statusCode": 403 }`
- Token đã được gửi đúng (verify qua Network tab)

### Phân tích

Decode JWT access token cho thấy **KHÔNG CÓ claim `tenant_id`** trong payload:

```json
{
  "exp": 1776248569,
  "iss": "http://localhost:8180/realms/qrtable",
  "sub": "f6a8e24d-dbe1-426f-99d8-7cecf57eb647",
  "azp": "management-app",
  "realm_access": { "roles": ["OWNER", "..."] },
  "email": "owner.1700000002@gmail.com"
  // ❌ THIẾU: "tenant_id": "tenant_a"
}
```

Trong khi đó, token từ `qrtable-bff` client thì CÓ `tenant_id` claim.

### Nguyên nhân gốc

**Keycloak Protocol Mapper chỉ được tạo cho `qrtable-bff` client, KHÔNG tạo cho `management-app` client.**

Bootstrap script (`tools/keycloak-bootstrap.sh`) sử dụng biến `client_id_internal` trỏ đến `qrtable-bff` (mặc định từ `KEYCLOAK_CLIENT_ID`):

```bash
KEYCLOAK_CLIENT_ID="${KEYCLOAK_CLIENT_ID:-qrtable-bff}"
# ... resolve client_id_internal từ KEYCLOAK_CLIENT_ID

# Mapper chỉ tạo cho qrtable-bff!
ensure_user_attribute_mapper "tenant_id-claim" "tenant_id" "tenant_id"
ensure_user_attribute_mapper "sub_role-claim" "sub_role" "sub_role"
```

Kết quả:

| Client           | `tenant_id-claim` mapper | `sub_role-claim` mapper |
| ---------------- | :----------------------: | :---------------------: |
| `qrtable-bff`    |          ✅ Có           |          ✅ Có          |
| `management-app` |         ❌ Thiếu         |        ❌ Thiếu         |

### Cách khắc phục

**Bước 1 — Hotfix:** Thêm mapper trực tiếp qua Keycloak Admin API:

```bash
# Thêm tenant_id mapper cho management-app client
curl -X POST \
  "http://localhost:8180/admin/realms/qrtable/clients/<mgmt-client-uuid>/protocol-mappers/models" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "tenant_id-claim",
    "protocol": "openid-connect",
    "protocolMapper": "oidc-usermodel-attribute-mapper",
    "config": {
      "user.attribute": "tenant_id",
      "claim.name": "tenant_id",
      "jsonType.label": "String",
      "id.token.claim": "true",
      "access.token.claim": "true",
      "userinfo.token.claim": "true",
      "multivalued": "false"
    }
  }'
```

**Bước 2 — Fix bootstrap script:** Update `tools/keycloak-bootstrap.sh` để lần sau tự tạo cho cả 2 clients:

```bash
# TRƯỚC: chỉ tạo cho qrtable-bff
ensure_user_attribute_mapper "tenant_id-claim" "tenant_id" "tenant_id"
ensure_user_attribute_mapper "sub_role-claim" "sub_role" "sub_role"

# SAU: tạo cho cả management-app
ensure_user_attribute_mapper "tenant_id-claim" "tenant_id" "tenant_id"
ensure_user_attribute_mapper "sub_role-claim" "sub_role" "sub_role"

mgmt_client_internal="$(curl -sS "...clients?clientId=management-app" | jq -r '.[0].id')"
if [[ -n "${mgmt_client_internal}" ]]; then
  saved_client_id="${client_id_internal}"
  client_id_internal="${mgmt_client_internal}"
  ensure_user_attribute_mapper "tenant_id-claim" "tenant_id" "tenant_id"
  ensure_user_attribute_mapper "sub_role-claim" "sub_role" "sub_role"
  client_id_internal="${saved_client_id}"
fi
```

### Bài học

- **Protocol mapper là per-client trong Keycloak** — mỗi client cần mapper riêng để claim xuất hiện trong JWT
- Khi hệ thống có nhiều client (BFF, management-app, customer-pwa), bootstrap script phải tạo mapper cho TẤT CẢ clients cần claim đó
- Luôn decode JWT để verify claims khi gặp 403 từ guard — đừng giả định token có đủ thông tin

## Lỗi #3: Keycloak User Attributes Bị Xóa

### Triệu chứng

- Trong quá trình debug lỗi #2, cố gắng cập nhật `tenant_id` attribute cho user qua Keycloak API
- Sau khi PUT, user bị mất `email`, `firstName`, `lastName` — chỉ còn `username`

### Nguyên nhân gốc

**Keycloak REST API `PUT /users/{id}` là REPLACE operation, không phải PATCH.** Nếu body không bao gồm tất cả fields hiện tại, chúng sẽ bị set về null/empty.

```bash
# ❌ SAI: chỉ gửi attributes, mất hết fields khác
curl -X PUT ".../users/{id}" -d '{"attributes": {"tenant_id": ["tenant_a"]}}'

# ✅ ĐÚNG: phải gửi đầy đủ tất cả fields
curl -X PUT ".../users/{id}" -d '{
  "email": "owner@...",
  "firstName": "owner",
  "lastName": "tenant_a",
  "enabled": true,
  "emailVerified": true,
  "attributes": {"tenant_id": ["tenant_a"], "sub_role": ["owner"]}
}'
```

### Cách khắc phục

Restore lại tất cả 7 users trong Keycloak với đầy đủ fields:

```bash
for user in superadmin owner manager waiter chef barista manager2; do
  curl -X PUT ".../users/${user_id}" \
    -d '{
      "email": "...",
      "firstName": "...",
      "lastName": "...",
      "enabled": true,
      "emailVerified": true,
      "attributes": {"tenant_id": ["..."], "sub_role": ["..."]}
    }'
done
```

### Bài học

- **Keycloak PUT API là destructive** — luôn GET user trước, merge changes, rồi PUT lại full payload
- Hoặc tốt hơn: viết helper function `update_user_attribute()` lấy user hiện tại, merge attribute, rồi PUT
- Không nên thao tác trực tiếp Keycloak API trong quá trình debug — dùng Admin Console (UI) an toàn hơn

## Lỗi phụ: Database Seed Issues

### Vấn đề 1 — Heredoc + Docker exec

```bash
# ❌ Heredoc multi-statement SQL qua docker exec bị silent fail
docker exec -i postgres psql -U postgres -d qrtable <<'EOF'
INSERT INTO tenants ...;
INSERT INTO categories ...;
EOF
```

**Fix:** Dùng `-c` riêng cho mỗi statement, hoặc wrap trong single-line query.

### Vấn đề 2 — tenant_id format mismatch

Ban đầu seed PostgreSQL với `tenant_id` là UUID (`550e8400-...`), trong khi Keycloak user attribute là string `"tenant_a"`.

**Fix:** Đồng bộ tất cả `tenant_id = 'tenant_a'` (string) xuyên suốt PostgreSQL, MongoDB, Keycloak.

### Bài học

- `tenant_id` là **string tùy ý**, không phải UUID — phải nhất quán giữa 3 hệ thống
- Luôn verify data consistency trước khi test: Keycloak attribute ↔ PostgreSQL column ↔ MongoDB field

## Lỗi #4: PWA 403 Forbidden — Missing x-tenant-id Header

### Triệu chứng

- Customer PWA gọi public API `/api/v1/menu` trả về `403 Forbidden`
- Response body: `{ "message": "Tenant is required", "error": "Forbidden", "statusCode": 403 }`
- Đây là public endpoint, không cần JWT auth

### Nguyên nhân gốc

PWA `customerApi` client **không gửi `x-tenant-id` header**. `TenantMiddleware` trên BFF áp dụng cho **tất cả routes** (cả public lẫn admin) và resolve tenant từ:

1. Header `x-tenant-id`
2. Subdomain (e.g., `tenant_a.localhost`)

PWA không dùng cả hai → `req[MetadataKey.TENANT_ID]` = `undefined` → controller gọi Catalog service với `tenantId = undefined` → query fail.

### Cách khắc phục

**File:** `apps/customer-pwa/src/constants/api.ts`

```typescript
// Thêm TENANT_ID config (env var hoặc default)
export const API_CONFIG = {
  DEFAULT_BASE_URL: import.meta.env.VITE_BFF_URL ?? 'http://localhost:3300/api/v1',
  TENANT_ID: import.meta.env.VITE_TENANT_ID ?? 'tenant_a', // ← THÊM MỚI
  // ...
};
```

**File:** `apps/customer-pwa/src/lib/api-client.ts`

```typescript
// Tự động gắn x-tenant-id header vào mọi request
export function customerApi<T>(path: string, options?: RequestInit): Promise<T> {
  return apiClient<T>(path, {
    ...options,
    baseUrl: API_CONFIG.DEFAULT_BASE_URL,
    headers: {
      'x-tenant-id': API_CONFIG.TENANT_ID, // ← THÊM MỚI
      ...options?.headers,
    },
  });
}
```

### Bài học

- Public endpoints vẫn cần `tenant_id` cho multi-tenant data isolation — chỉ là không cần JWT auth
- Trong Phase 1, tenant resolve từ env/config là đủ; sau này sẽ resolve dynamic từ URL slug hoặc subdomain
- `TenantMiddleware` nên log warning rõ ràng hơn khi không resolve được tenant trên public routes

## Lỗi #5: PWA 404 Not Found — Sai BFF Port

### Triệu chứng

- PWA gọi `http://localhost:3000/api/v1/menu` → nhận `OPTIONS 404 Not Found`
- CORS preflight bị Next.js (management-app) intercept thay vì BFF NestJS

### Nguyên nhân gốc

PWA `api.ts` default URL trỏ đến **port 3000** — đây là Next.js management-app, **không phải BFF**. BFF thực tế chạy ở **port 3300** (do Nx serve config).

| Port | Service                |
| ---- | ---------------------- |
| 3000 | Next.js management-app |
| 3300 | NestJS BFF             |
| 5173 | Vite customer-pwa      |

### Cách khắc phục

**File:** `apps/customer-pwa/src/constants/api.ts`

```typescript
// TRƯỚC
DEFAULT_BASE_URL: import.meta.env.VITE_BFF_URL ?? 'http://localhost:3000/api/v1',

// SAU
DEFAULT_BASE_URL: import.meta.env.VITE_BFF_URL ?? 'http://localhost:3300/api/v1',
```

### Bài học

- BFF port 3000 là mặc định trong code nhưng Nx serve có thể override — luôn kiểm tra `lsof -iTCP -sTCP:LISTEN` để xác nhận port thực tế
- Nên dùng env var (`VITE_BFF_URL`) thay vì hardcode port
- Port conflict giữa Next.js (3000) và NestJS default (3000) cần được document rõ trong project setup

## Lỗi #6: PWA Blank Screen — API Response Shape Mismatch

### Triệu chứng

- PWA menu page (`/menu`) hiện trắng hoàn toàn, không có error message
- API call thành công (200 OK), data trả về đúng
- Console không báo lỗi rõ ràng (React error boundary không bắt được)

### Nguyên nhân gốc

BFF trả về response dạng `{ data: { categories: [...] } }`. Sau khi `apiClient` unwrap → `{ categories: [...] }` (object).

Nhưng `useFullMenuQuery` hook và `menu-page.tsx` xử lý `data` như **array trực tiếp** (`menu.length`, `menu.map()`, `menu.flatMap()`). Gọi `.length` trên object trả `undefined` → condition `menu.length === 0` = false → render tiếp → crash khi `.map()`.

```typescript
// API trả về: { categories: [...] }  (object)
// Code expect: PublicMenuCategory[]   (array)

// menu.length → undefined (không crash nhưng không render gì)
// menu.map() → TypeError (crash silently trong React)
```

### Cách khắc phục

**File:** `libs/shared/types/src/lib/public-menu.types.ts`

```typescript
// TRƯỚC
export type PublicMenuResponse = PublicMenuCategory[];

// SAU — match API response shape
export type PublicMenuResponse = {
  categories: PublicMenuCategory[];
};
```

**File:** `apps/customer-pwa/src/features/menu/hooks/use-menu-query.ts`

```typescript
// TRƯỚC — pass raw response (object) to components
queryFn: menuService.getFullMenu,

// SAU — extract categories array
queryFn: async () => {
  const response = await menuService.getFullMenu();
  return response.categories;
},
```

### Bài học

- TypeScript types phải match **actual API response** — luôn verify bằng `curl` hoặc Network tab trước khi định nghĩa types
- Blank screen thường do data shape mismatch — React không crash nổi khi gọi method trên wrong type
- Nên có runtime validation (Zod) cho API responses, không chỉ dựa vào TypeScript compile-time types

## Lỗi #7: Upload Image — Wrong FormData Field Name

### Triệu chứng

- Upload ảnh menu item trả về `400 Bad Request`
- Response: `{ "message": "Unexpected field - file", "statusCode": 400 }`

### Nguyên nhân gốc

Frontend `uploadFile()` utility gửi FormData với field name **`file`**, nhưng BFF dùng `FileInterceptor('image')` — expect field name **`image`**.

```typescript
// Frontend (libs/frontend/utils/src/lib/upload-client.ts)
formData.append('file', file);     // ❌ field name = 'file'

// BFF (menu-item.controller.ts)
@UseInterceptors(FileInterceptor('image', ...))  // expect field name = 'image'
```

### Cách khắc phục

**File:** `libs/frontend/utils/src/lib/upload-client.ts`

```typescript
// TRƯỚC
formData.append('file', file);

// SAU
formData.append('image', file);
```

### Bài học

- Multer `FileInterceptor` field name phải **exact match** với FormData field name
- Nên define constant cho upload field name, share giữa FE và BE
- Error message `"Unexpected field - file"` nghĩa là Multer nhận field `file` nhưng chỉ expect `image`

## Lỗi #8: Upload Image 500 — Cloudinary Account Disabled

### Triệu chứng

- Sau fix field name, upload trả về `500 Internal Server Error`
- Response: `{ "message": "Image upload failed", "statusCode": 500 }`
- BFF log: `Upload failed: disabled customer`

### Nguyên nhân gốc

Cloudinary account cũ (cloud name: `dnbumbcm3`) **đã bị vô hiệu hóa** ("disabled customer"). Credentials trong `.env` vẫn trỏ đến account này.

### Cách khắc phục

1. Tạo Cloudinary account mới
2. Update `.env` với credentials mới
3. **Restart BFF** — vì NestJS `ConfigModule` load env lúc khởi động, hot-reload không đọc lại `.env`

### Bài học

- Cloudinary free plan có thể bị disable nếu không hoạt động lâu
- `.env` changes cần **restart process** — NestJS không hot-reload env vars
- CloudinaryService nên log rõ error message từ Cloudinary API thay vì swallow thành generic "Image upload failed"

## Lỗi #9: Upload Image 500 — Cloudinary `format: 'auto'` Not Supported

### Triệu chứng

- Sau khi đổi Cloudinary account mới, upload vẫn 500
- BFF log: `Cloudinary upload error: {"message":"Invalid extension in transformation: auto","http_code":400}`

### Nguyên nhân gốc

`CloudinaryService.uploadToCloudinary()` gửi option `format: 'auto'` — đây là **tính năng premium** của Cloudinary, **không hỗ trợ trên free plan**.

```typescript
// Cloudinary upload options
const result = await this.uploadToCloudinary(file, {
  folder,
  public_id: publicId,
  resource_type: 'image',
  format: 'auto', // ❌ Premium feature — free plan reject
  quality: 'auto',
  transformation: [{ width: DEFAULT_LARGE_WIDTH, crop: 'limit' }],
});
```

### Cách khắc phục

**File:** `libs/providers/cloudinary/src/lib/cloudinary.service.ts`

```typescript
// TRƯỚC
const result = await this.uploadToCloudinary(file, {
  folder,
  public_id: publicId,
  resource_type: 'image',
  format: 'auto',
  quality: 'auto',
  transformation: [{ width: DEFAULT_LARGE_WIDTH, crop: 'limit' }],
});

// SAU — bỏ format: 'auto', chuyển quality vào transformation
const result = await this.uploadToCloudinary(file, {
  folder,
  public_id: publicId,
  resource_type: 'image',
  transformation: [{ width: DEFAULT_LARGE_WIDTH, crop: 'limit', quality: 'auto' }],
});
```

### Bài học

- Cloudinary free plan có nhiều giới hạn — `format: 'auto'` (f_auto), eager transformations, v.v. đều cần paid plan
- Nên test Cloudinary integration với **cùng plan** sẽ dùng trong production
- Error handling trong `uploadToCloudinary` ban đầu swallow Cloudinary error → thêm logging chi tiết giúp debug nhanh hơn
